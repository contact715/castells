# Стек и слои пульта

29 августа 2026. Ответ на вопрос владельца «это Next.js? какой стек собираем?
напиши оптимальную архитектуру».

Всё, что ниже помечено словом «замер», измерено в этот день, а не взято из
памяти. Команды воспроизведения приведены рядом.

---

## 1. Короткий ответ: это НЕ Next.js

Замер (`cat services/package.json`, `ls node_modules | wc -l`):

| | Пульт Castells | Кабинет Mosco для сравнения |
|---|---|---|
| Зависимостей в package.json | **0** | 70 |
| Пакетов в node_modules | **0** | 620 |
| Размер node_modules | **0 МБ** | 737 МБ |
| Строк кода | 5 047 | сотни тысяч |
| Сбор всех данных | **40 мс** | — |
| Деплой на Railway | **26 с** | минуты |

Пульт — это голый Node.js версии 20 и выше. Встроенный HTTP-сервер, модули
ESM (`.mjs`), рендер страницы обычной сборкой строк. Ни React, ни Next.js, ни
сборщика, ни базы данных. Данные лежат в файлах-профилях `clients/<id>.mjs`.

**И это оказалось правильным решением, а не бедностью.** Пульт сегодня только
ЧИТАЕТ: собирает состояние из профилей и показывает. Для чтения фреймворк не
даёт ничего, а стоит 737 МБ, минут сборки и семидесяти зависимостей, каждую из
которых надо обновлять и чинить.

---

## 2. Что уже устроено правильно

Замер связей (`grep '^import' lib/*.mjs`) показал главное: **ядро уже чистое.**

```
access.mjs    — не тянет ничего
catalog.mjs   — не тянет ничего
stages.mjs    — не тянет ничего
profile.mjs   — только соседей по домену
report.mjs    — только соседей по домену
plan.mjs      — только соседей по домену
```

Ни один модуль домена не знает про файловую систему, сеть, HTTP или HTML. Это
самое ценное имущество проекта: пока домен ничего не знает про оболочку, любую
оболочку можно заменить, не трогая правила работы с клиентом.

Именно поэтому вопрос «переходить ли на Next.js» здесь дешёвый. В большинстве
проектов он дорогой, потому что домен размазан по компонентам.

---

## 3. Что было устроено неправильно (исправлено 29 августа)

Три дефекта, все видны в связях модулей.

**3.1. Чтобы отдать данные, сервер тянет рисование.** `server.mjs` импортирует
`dashboard.mjs`, потому что там же лежит сбор данных. То есть машина, которой
нужен JSON, загружает модуль, умеющий рисовать HTML. Сегодня это стоит
миллисекунды, но это уже не граница слоёв, а её отсутствие.

**3.2. Представление лежит в папке домена.** `lib/shell.mjs` и `lib/theme.mjs`
— это HTML и CSS, они соседствуют с `lib/access.mjs`, где правила доступов.
Разные скорости изменения в одной папке: оформление правится каждую неделю,
правила доступов — раз в квартал.

**3.3. Сбор данных не назван отдельно.** Функция `собратьПроекты` живёт внутри
`dashboard.mjs`. Это чтение хранилища, и когда хранилищ станет два (файлы и
база), его придётся выковыривать оттуда.

Ни один из трёх не мешал в тот день. Все три подорожали бы, как только
появится второй потребитель данных или второе хранилище, — поэтому раскладка
по слоям сделана сразу, до прихода живых данных. Что получилось, описано в §4;
границы слоёв теперь проверяет самопроверка, а не договорённость.

## 4. Каноничная архитектура: четыре слоя

Правило одно: **зависимости идут только внутрь.** Внешний слой знает про
внутренний, внутренний про внешний — никогда.

```
      ┌──────────────────────────────────────────────┐
      │  ОБОЛОЧКИ (web/)                             │
      │  http-api · html-рендер · cli · будущий Next │
      └───────────────────┬──────────────────────────┘
                          │ знает
      ┌───────────────────▼──────────────────────────┐
      │  СЛУЧАИ РАБОТЫ (app/)                        │
      │  «собрать состояние проектов»                │
      │  «прогнать стадию» · «собрать отчёт»         │
      └───────────────────┬──────────────────────────┘
                          │ знает
      ┌───────────────────▼──────────────────────────┐
      │  ХРАНИЛИЩЕ (store/)                          │
      │  профили из файлов · метрики из базы         │
      └───────────────────┬──────────────────────────┘
                          │ знает
      ┌───────────────────▼──────────────────────────┐
      │  ЯДРО (core/)   ← уже построено, не трогать  │
      │  profile · access · stages · report ·        │
      │  catalog · plan — чистые правила, без ввода- │
      │  вывода                                      │
      └──────────────────────────────────────────────┘
```

Что меняется физически по сравнению с сегодняшним днём:

| Сейчас | Станет | Зачем |
|---|---|---|
| `lib/{profile,access,stages,report,catalog,plan}.mjs` | `core/` | назвать ядро ядром |
| `lib/{shell,theme}.mjs` | `web/view/` | оформление меняется в десять раз чаще правил |
| `собратьПроекты` внутри `dashboard.mjs` | `store/projects.mjs` | чтение хранилища — отдельная обязанность |
| `dashboard.mjs` | `web/render.mjs` | только рисование, данные приходят готовыми |
| `server.mjs` | `web/http.mjs` | только маршруты и вход |
| `run.mjs` | `web/cli.mjs` | оболочка, а не ядро |

Это перекладывание файлов и правка импортов, без изменения поведения. Один
вечер работы, самопроверки ловят ошибки сразу.

## 5. Хранилище: где файл, где база

Развилка, которую чаще всего решают неправильно — «раз есть база, кладём всё
в базу».

**В файлах остаются профили клиентов.** Профиль — это решение о клиенте: какие
услуги ведём, какие доступы есть, какие города обслуживаем. Такое решение
должно попадать в git: его видно в истории, можно посмотреть, кто и когда
поменял, и откатить. Форма ввода этого не даёт.

**В базу уходит всё, что накапливается со временем:**

- показатели из Search Console по датам,
- данные счётчика посещений,
- история ежемесячных отчётов (что ушло клиенту и когда),
- черновики текстов и их состояние проверки,
- журнал прогонов стадий.

Причина простая и проверяемая: это временны́е ряды. По ним спрашивают «что
изменилось за месяц», их пишут ежедневно и параллельно. Файл на таком объёме
разъезжается, а два процесса, пишущие в один JSON, затирают друг друга.

**Что взято (29 августа, шаг 3 выполнен):** PostgreSQL 17 отдельным сервисом
`castells-db` в том же проекте Railway, с постоянным диском на
`/var/lib/postgresql/data` — без диска данные исчезли бы при первом
перезапуске. Пульт ходит к нему по внутренней сети
(`${{castells-db.DATABASE_URL}}`), наружу база не выставлена. Доступ — через
`store/db.mjs`, ядро о базе не знает.

Драйвер выбран замером: `postgres` (postgres.js) — ноль собственных
зависимостей, 384 КБ; `pg` — шесть прямых зависимостей. Это первая и пока
единственная зависимость проекта.

**Чего НЕ делать:** не переносить профили в базу «для единообразия». Два
источника правды об одном клиенте разъедутся, вопрос только в сроке.

## 5а. Проверки: свой прогон вместо фреймворка

Это тоже часть стека, и её легко не заметить. Замер: `services/self-test.mjs`
— **178 проверок, ноль внешних зависимостей**, запуск `node self-test.mjs`,
считанные секунды.

Написано без Jest и без Vitest, потому что для проверки чистых функций
фреймворк даёт только имена: `describe`, `it`, `expect`. Взамен он приносит
свой запускатель, свой формат, свою настройку и ещё десятки пакетов. При нуле
зависимостей во всём проекте это была бы самая тяжёлая часть.

**Где проверки живут в слоях.** Сегодня они в одном файле на всё. При
раскладке по слоям файл делится по той же границе:

```
core/*.test.mjs      правила: доступы, стадии, отчёт, план
store/*.test.mjs     чтение профилей, позже — база
web/*.test.mjs       маршруты, вход, разметка
```

Причина не в порядке, а в скорости: проверки ядра не требуют ни сервера, ни
базы и должны идти мгновенно, чтобы их запускали на каждую правку.

**Когда менять.** Свой прогон перестаёт окупаться там, где начинается
асинхронное и браузерное: компоненты, формы, состояние. То есть в тот же
момент, что и переход на Next.js. Тогда берём Vitest — он ставится вместе с
каркасом и не тянет отдельную вселенную. Проверки ядра при этом переносятся
почти дословно: они на чистых функциях.

## 6. Контракт: один вход для всех

Сейчас есть `/api/projects`, и он отдаёт то же, что видно на странице. Это
надо закрепить как правило:

**Любой потребитель — страница, агент, будущий Next.js, телефон — получает
данные только через `/api/*`. Никто не читает файлы напрямую.**

Пока это стоит ноль: адрес уже есть. Но именно это правило делает смену фронта
дешёвой. Без него фронт прирастает к чтению файлов, и переезд превращается в
переписывание.

---

## 7. Когда переходить на Next.js

Не «когда вырастем», а по конкретному признаку.

**Признак: человек должен ИЗМЕНЯТЬ данные через интерфейс.**

Пока пульт показывает состояние, самописный рендер выигрывает: 40 мс на сбор,
26 секунд на выкладку, ноль зависимостей. Как только появится хотя бы одно из
списка, он начинает проигрывать:

- утверждение черновика текста кнопкой «принять / вернуть»,
- правка профиля клиента через форму,
- отметка «доступ получен» прямо в пульте,
- графики показателей с выбором периода,
- несколько человек с разными правами.

Каждый пункт по отдельности можно дописать руками. Три и больше — уже дешевле
на фреймворке: формы, состояние, проверка ввода, обновление части страницы.
Писать это самому четвёртый раз — тратить время на решённую задачу.

**Стек на этот случай** (не сегодня, а когда признак наступит):

| Слой | Что брать | Почему это |
|---|---|---|
| Каркас | Next.js, App Router, TypeScript | тот же, что в Mosco: одна голова на два продукта |
| Оформление | Tailwind + токены Mosco | уже перенесены в `web/view/theme.mjs`, переносятся один в один |
| База | PostgreSQL на Railway | уже в том же проекте |
| Доступ к базе | Drizzle | ближе к SQL, легче объяснить, чем Prisma |
| Вход | сегодняшний пароль, дальше Auth.js | роли понадобятся, когда появится клиентский доступ |
| Проверки | Vitest | ставится с каркасом; проверки ядра переносятся дословно |
| Ядро | **остаётся как есть** | оно чистое, его переносят импортом |

Последняя строка — главная. Переход на Next.js не должен трогать `core/`.
Если тронул, значит слои построены неправильно.

## 8. Порядок работ

По убыванию отношения пользы к цене.

1. **Разложить по слоям** (вечер). Файлы на места, импорты поправить, поведение
   не меняется. Делает дешёвыми все следующие шаги.
2. **Закрепить `/api/*` как единственный вход** (час). Правило плюс проверка,
   что рендер не читает файлы сам.
3. ~~**Поднять Postgres и завести `store/`**~~ — сделано 29 августа. База,
   диск, схема при старте, журнал прогонов пишется из оркестратора. Таблица
   не оставлена пустой: каждая стадия пишет строку, включая незапущенные —
   иначе через месяц на вопрос «почему у клиента ничего не двигалось» ответом
   была бы пустота.
4. **Счётчик посещений** (по документу — второе, что закрывает стадию 6).
5. **Search Console** — упирается в доступ клиента, а не в код.
6. **Next.js** — только когда наступит признак из раздела 7.

Пункты 1 и 2 стоит сделать до того, как в пульт придут живые данные. После —
станет дороже, потому что придётся двигать работающее.

## 9. Что решает владелец, а не я

Три развилки, где выбор меняет архитектуру, а не оформление.

**9.1. Кто будет пользоваться пультом?** Только мы вчетвером — хватит общего
пароля, который сейчас стоит. Если клиенты будут смотреть свой проект — нужны
учётные записи, роли и разделение данных, и это меняет и вход, и хранилище.

**9.2. Пульт только показывает или им работают?** Если из него будут запускать
стадии, утверждать черновики и отмечать доступы — признак из раздела 7 наступил
уже сегодня, и Next.js имеет смысл планировать сразу.

**9.3. Готовы ли платить за данные о запросах?** Стадия 1 без них не
закрывается ничем — это вопрос денег, а не кода (см. ARCHITECTURE.md §8).

## 10. Чего я не проверял

- **Нагрузку.** Четыре проекта и один пользователь — измерять нечего. При
  сорока проектах сбор в 40 мс вырастет линейно, это не проблема, но проверять
  надо будет замером, а не расчётом.
- **Стоимость Postgres на Railway** в этом тарифе — не смотрел. Известно
  только общее правило Railway: диск считается по $0.15 за ГБ-месяц, сам
  сервис — по потреблению. Сумму в месяц назвать не могу.
- **Перенос токенов Mosco в Tailwind.** Значения выписаны и работают в CSS,
  но конфиг Tailwind под них я не собирал и не проверял.
- **Auth.js с общим паролем.** Схема «один пароль на всех» в него ложится
  плохо; если роли понадобятся, схему входа придётся продумывать заново.
